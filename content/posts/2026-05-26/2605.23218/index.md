基础协议：面向智能体社会的协调层

> 导读摘要：这篇论文不是在发明又一个“Agent 通信协议”，而是在补一层更底座的协调基础设施。作者提出 Foundation Protocol（FP），把智能体、工具、人、资源和组织统一建模为图中的可寻址实体，并把身份、授权、会话、事件、结算、来源追踪和审计放进同一套协议语义里，目标是在开放多智能体网络中，同时保留可组合性、经济交换能力与现实世界所需的可治理性。

## 一、问题从“模型能力”转向“协调能力”

作者的出发点很明确：当自主智能体不再只是被人调用的一次性工具，而是能持续在线、跨服务行动、彼此协作、代表用户做决策的参与者时，系统瓶颈就不再主要是模型会不会推理，而是**谁能和谁协作、按什么权限协作、协作后如何结算与追责**。

![​[Fig1]](figures/Fig1.png)

上图给了论文最重要的背景框架：从 Web 1.0 到更接近 Web 4.0 的阶段，网络能力在不断增强，但随之放大的也是协调失灵。过去互联网擅长传内容、连资源；一旦进入“代理代表人行动”的阶段，身份、责任、政策和治理就不能继续留在应用层零散拼接。论文因此提出一个判断：未来网络要分发的不只是信息，还包括“行动能力”，那么协议层就必须显式编码授权、证据和监督。

这也是作者反复强调的一点：传统软件里，通信和执行通常还能分开；但在智能体系统里，一条消息可能触发代码执行、资源消耗、支付、委托甚至策略变更。于是，协议边界本身就成了安全边界、治理边界和经济边界。

## 二、FP 的核心主张：用图原生协议统一异构参与者

FP 的核心不是某一种消息格式，而是一种**图原生的协调建模方式**。它把智能体、工具、资源、人类、机构、组织都视为可寻址实体；再把关系、成员资格、会话、活动、事件、凭证等提升为一等协议对象。也就是说，FP 关心的不是“两个端点如何发消息”，而是“一个开放社会中的各类参与者如何以可验证、可治理的方式组织协作”。

![​[Table3]](figures/Table3.png)

这张表从“智能密度”视角解释了作者为什么认为现在需要这种基础层。随着工业革命一路演进，真正稀缺的东西逐步从单机能力转向大规模组织知识、协作与执行。映射到 AI 场景，就是：模型推理成本会继续下降，但跨主体协调、验证、追踪和治理会变得更稀缺。FP 试图补上的，正是这个稀缺层。

在这个意义上，FP 的目标不是替代已有生态，而是给开放多智能体社会提供一套共同底座，让系统能回答几类现在很难统一回答的问题：

- 谁在发起一个动作，代表谁发起？
- 这个动作的权限从哪里来，边界在哪里？
- 多个智能体如何形成组织、角色与成员关系？
- 执行过程产生的事件、收据、结算如何串成证据链？
- 监管、审计、策略约束如何嵌入协作流程本身？

## 三、方法设计：四个平面 + 配置/桥接层

论文方法部分最重要的图，就是 FP 的整体架构。

![​[Fig2]](figures/Fig2.png)

作者把系统拆成四个核心平面，加一个配置/画像与桥接层。这样做的目的，是只把跨场景稳定的最小语义固化在核心里，把易变化的实现留给外层适配。

### 1. 实体与信任平面

这是最底层的“谁是谁”问题。FP 在这里定义实体、身份、关系、角色、委托与信任锚。重点不是只有单个 Agent 身份，而是连组织、机构、人类、工具都能进入同一个地址空间。这样，多方协作时不必每个协议各自维护一套割裂的身份语义。

### 2. 传输与路由平面

这一层负责发现、寻址、连接和消息承载。作者不试图绑定某一种底层传输，而是允许不同 transport 独立演进。核心思想是：传输可以多样，但上层语义不能漂移，否则跨协议拼接后会丢失身份、上下文和责任关系。

### 3. 交互与组织平面

这是论文最有“社会基础设施”味道的一层。FP 不只支持点对点交互，还原生支持多方组织、事件驱动协作、会话上下文、活动流和跨主体协同。作者认为，未来主流工作流不是单一 Agent 调单一工具，而是多个主体在一个持续存在的组织关系中合作。

### 4. 监管与监督平面

这一层体现了 FP 与很多现有 Agent 协议的根本区别：策略、来源追踪、审计、合规不是外挂，而是协议原语。系统需要在交互发生时就能挂接政策执行点、证据记录和审计钩子，而不是等事故发生后再拼日志。

### 5. 配置/画像与桥接层

左侧的 Profiles & Bridges 说明 FP 采用的是“桥接而非替代”路线。不同身份方法、底层传输、特定领域协议都可以通过配置和桥接接入。也就是说，FP 更像控制平面与语义平面，而非单一封闭栈。

![​[Table2]](figures/Table2.png)

这张边界图把 FP 与 MCP、A2A、A2UI、DIDComm、ANP、UCP 等放在一起比较，论文的立场很清楚：这些协议分别解决工具访问、Agent 协作、界面委托、身份通信、开放网络发现或商业交易等局部问题，而 FP 负责把它们共享却又长期缺失的横切问题标准化——统一实体、组织关系、审计证据、经济凭证和治理接口。

## 四、FP 的最小语义对象：把协作、执行、结算、审计串起来

论文还给出一组最小但稳定的核心对象，用来组成整套协议语义。

![​[Table7]](figures/Table7.png)

从这张对象速览表可以看出，FP 不是把一切都压缩进“消息”概念，而是显式区分了几类对象：

- **Entity**：参与者本身，可以是 Agent、工具、人、组织等。
- **Session**：协作发生的上下文容器。
- **Activity**：具体任务或工作单元。
- **Envelope / Event**：承载通信与过程记录。
- **Receipt / Settlement**：把计量、收据、结算纳入协议。
- **Provenance**：来源追踪与证据链。

这种设计有两个方法上的好处。

第一，它把“通信”和“执行后果”重新接上了。传统接口往往只负责把请求送到；FP 则要求把执行痕迹、责任归属、支付或资源消耗结果也纳入同一语义链条。

第二，它让监管与经济活动可以原生嵌入协作。只要对象层次分清楚，后续无论接入计费、争议处理、预算控制还是审计系统，都不需要再从杂乱日志里逆向还原上下文。

## 五、场景化验证：AI 公司生命周期如何映射到 FP

这篇论文没有传统意义上的 benchmark，而是采用架构论证 + 典型场景展开。最核心的场景是“AI 公司”生命周期：一个由多个智能体组成的组织，如何从建立、招募、协作、执行一路走到结算和审计。

![​[Fig3]](figures/Fig3.png)

这个例子很重要，因为它把作者的抽象主张落到一个持续运转的组织场景里。流程大致包括：

1. 创建组织与初始身份；
2. 发现并招募外部能力或服务；
3. 基于角色和权限分配任务；
4. 多智能体跨边界协作并执行；
5. 对执行结果计量、结算；
6. 形成可审计凭证并接受监督。

作者想说明的是：当 Agent 系统开始像组织一样长期存在时，问题就不再是“接口是否可调用”，而是“组织是否可治理”。发现、雇佣、委托、预算、结算、审计必须落在一套连续协议里，否则系统就会在协议边界处丢失证据和责任。

![​[Table11]](figures/Table11.png)

这张表进一步把 AI 公司场景拆成“阶段—模块—职责”的对应关系，展示 FP 各平面如何协同。前期重在实体、身份和关系建立；中期重在会话、活动、事件和协作；后期重在收据、结算、审计与争议处理。它说明 FP 的价值不在单一调用成功，而在于支撑完整、持续、可回溯的组织级流程。

## 六、设计目标与论文结论：开放采用，但把问责做成硬约束

论文最后的设计立场可以概括成三句话。

首先，**FP 要桥接现有协议，而不是推倒重来**。这让它更可能被渐进采用：已有系统可以继续用自己的工具协议、身份协议或商业协议，只需把共享的协调语义对齐到 FP。

其次，**FP 把身份、授权、政策、来源追踪和审计提升为协议层原语**。这比在应用层打补丁更强，因为它要求系统从一开始就保留责任链，而不是事后补日志。

![​[Fig4]](figures/Fig4.png)

这张图很好地总结了作者的方法取向：随着 Agent 执行越来越便宜，真正稀缺的将是验证能力、可证明来源、责任承保和治理能力。换句话说，未来竞争力不只是谁能让 Agent 更快行动，而是谁能让 Agent **可验证地行动**。

最后，**FP 试图把“协调”本身做成共享基础设施**。论文的核心结论不是某个实验指标领先，而是一个系统设计判断：在开放多智能体社会里，如果没有统一的协调层，互操作会脆弱、审计会断裂、治理会碎片化，最终最容易走向封闭的一体化平台；而 FP 想避免的，正是这种由协调成本推出来的集中化路径。

整体来看，这是一篇非常“方法论驱动”的论文。它没有给出传统性能实验，但架构主线相当清晰：  
**用图原生实体建模统一异构参与者，用四层平面隔离稳定语义与可变实现，用会话、活动、事件、收据、来源追踪组成证据链，再用桥接机制接入现有协议生态。**  
如果你关心的不是“某个 Agent 框架怎么用”，而是“未来开放 Agent 社会靠什么基础设施才能真正运转”，这篇论文值得细读。
